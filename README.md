# 骰趣 · 微信骰宝小程序

前后端代码均位于本目录。默认是**可以在微信开发者工具中直接试玩的本地演示模式**，同时提供 CloudBase 云函数代码。仅使用虚拟积分。

## 现在可以做什么

- 下注大小、任意豹子、指定豹子、总点数、出现某点；支持多选、不同筹码、长按减筹码和清空。
- 透明骰盅摇动、三颗立体骰子盅内翻滚、点数落定、桌面命中高亮和结果明细。
- 积分钱包和分页流水；新用户初始 500 积分，按连续签到天数发放不同奖励，展示当天金额、七天预览和完整奖励表。
- 模拟广告完整观看 6 秒，每日成功领取第 1/2/3 次依次奖励 200/500/1,000 分；提前关闭、离开页面不奖励、不占领取次数。
- 分享给好友或群聊后，返回钱包自行确认领取 100 分，不限次数；取消分享不自动奖励，同一笔确认重试不重复发放。
- 好友排行、生成与接受邀请、移除好友；修改昵称后同步到排行。
- 断网/响应丢失后使用原请求恢复结算；重复下注、签到、广告与分享领奖均防重。

**演示模式说明**：数据存在本机微信 Storage，内置两位有明确标注的示例好友，不读取微信好友。清除小程序缓存会清除演示数据。演示邀请码不能跨设备建立关系；真实邀请功能需要云端模式。演示广告是倒计时交互，不是实际广告、不会产生广告收入。

## 1. 启动本地演示

本地工作目录已生成构建产物；Git 仓库不包含 `dist`、`node_modules` 或测试临时产物。从 GitHub 克隆后，需要先执行下方的依赖安装和构建命令。打开微信开发者工具，导入项目根目录（迁移后本地路径为 **`D:\MyAgent\Empower\game_mock`**），选择小程序项目；根目录 `project.config.json` 已指向 `dist/miniprogram`，默认 AppID 是 `touristappid`。

不需要启动 HTTP 服务，不需要云环境，不需要真实广告位。若工具不允许无 AppID 导入，使用工具提供的测试号即可；云端功能仍需自己的 AppID。

如需重新安装或构建，在本目录执行：

```powershell
npm ci --ignore-scripts
npm run build
```

使用 Node.js 22 或 24。开发时编辑 `apps/`、`services/`、`packages/` 下的源文件，之后重新构建；不要直接改 `dist/`。构建只写本项目的产物，不会部署云函数。

### 试玩顺序

1. 骰宝页选择 10/50/100 筹码，点选一个或多个玩法，点击“摇盅开奖”。
2. 查看桌面结果条，点“明细”查看投入、返还与净变动；钱包中能看到对应流水。
3. 钱包页签到，再依次体验三次 6 秒模拟广告（开始间隔至少 15 秒）；中途关闭可以验证不发奖励。分享后回钱包点“已分享，领取 100 分”，没有发送则点“未分享，取消领取”。好友页发起的分享也到钱包统一确认。
4. 我的页面修改昵称，切到好友排行查看更新后的昵称与积分。
5. 退出再进入，本机积分和昵称仍保留。

## 3. 切换到真实云端

以下步骤需要自己的微信账号和云环境。本次没有开通资源、上传代码或部署。

1. 将根目录 `project.config.json` 的 `appid` 改为你的小程序 AppID。
2. 在 `apps/miniprogram/config.ts` 将 `mode` 改为 `cloud`，填入对应 `cloudEnv`。
3. 使用 CloudBase **传统模式文档数据库**。按照 `cloudbase/database.json` 创建全部集合、索引，并把每个集合的客户端权限设为仅管理端访问（客户端读写均禁止）。不要给客户端开放钱包写入权限。
4. 执行 `npm run build`，在微信开发者工具中上传并部署 `dist/cloudfunctions/gameApi`，安装其独立依赖。入口为 `index.main`，Node.js 24 LTS 优先（构建语法也兼容 22），超时建议 20 秒。
5. 云函数部署配置包含 `security.msgSecCheck` 权限。昵称修改调用内容检查，检查失败不保存昵称。需要在实际环境确认小程序与云环境关联、开放接口权限和身份上下文。
6. 用两个测试微信号完成建档、下注、签到、邀请、改昵称与排行联调。邀请卡片从首页进入，随后在好友排行页明确点击接受。
7. 验证数据库事务、索引、日志及 iOS/Android 真机表现后，再处理平台类目和发布审核。

数据库 SDK 使用 `@cloudbase/node-sdk` 的原生 `set(value)` 形式，不能替换成小程序客户端 SDK 的 `set({data: value})`。云事务由 SDK 处理提交、回滚和有限冲突重试。

## 4. 激励视频接入

前端已经实现 `wx.createRewardedVideoAd`、加载/展示、`onClose`、`onError` 与监听器清理。只有 `isEnded === true` 才向后端请求奖励；错误、跳过和不明确的关闭状态均不请求发放。

真实云端默认关闭广告，需要有效广告位和流量主接入条件。在 `gameApi` 云函数环境变量中设置：

| 环境变量 | 值 |
| --- | --- |
| `AD_REWARDS_ENABLED` | `true` |
| `REWARDED_AD_UNIT_ID` | 你的 `adunit-…` 激励视频广告位 ID |

广告位从服务端返回，前端不需要重复配置。本项目的广告位 ID 不是密钥；账号凭证不得写入代码。

后端先建立广告会话，再按会话归属、有效期、观看时长下限、每日次数和幂等标记发放。云端开始会话间隔为 60 秒，会话有效期为 10 分钟；演示间隔为 15 秒。奖励归属会话创建的北京时间自然日，跨日会话不兑现。

**真实性边界**：当前接入使用客户端完整观看事件；服务器限额与会话校验并不是微信服务端观看证明，也不能阻止修改过的客户端伪造“已看完”。项目未假设或编造微信 SSV 回调协议。正式开放广告奖励前，需要按实际广告产品支持能力评估服务端验真；目前代码适用于本项目的低价值、不可兑现虚拟积分奖励。没有广告位时维持云端广告关闭，不会暗中以模拟观看发真实奖励。

云端当前最短会话时长为 15 秒。如果广告结束过快，页面会保留领奖标识，稍后点击“确认上一笔广告奖励”重试；该时长只是限速约束，不是广告完成证明。后续应按真实广告产品配置调试。

官方参考：[腾讯激励视频组件说明](https://intl.cloud.tencent.com/ind/document/product/1219/68596)。该资料用于核对事件使用方式，实际微信广告资格和能力以自己的平台配置为准。

## 5. 规则、奖励及一致性

配置位于 `packages/domain/index.ts`，当前版本 `sicbo-v1`。使用项目娱乐规则，不声称复制某家澳门场所的赔率。

| 玩法 | 净赢倍数 |
| --- | --- |
| 大/小 | 1；豹子均不命中 |
| 任意豹子 | 24 |
| 指定豹子 | 150 |
| 总点数 4/17、5/16、6/15、7/14、8/13 | 60、30、17、12、8 |
| 总点数 9/10/11/12 | 6 |
| 某点出现 1/2/3 次 | 1、2、3 |

命中返还 = 该项投入 ×（1 + 净赢倍数）；不命中返还 0。多个选项独立计算。积分均为整数，单局总投入最多 500，余额不允许为负或超过 10 亿。

钱包、局结果和投入/返还流水在一个事务中提交。请求 ID 与规范化请求摘要关联，同一个请求最多产生一个结果。同一 ID 修改内容会被拒绝。客户端保留未确认请求，恢复时只查询或重试原请求。

签到记录以用户与北京时间日期防重。奖励按连续签到天数计算，断签从第 1 天重新开始，每天北京时间 00:00 更新：

| 连续签到天数 | 当日积分 |
| --- | ---: |
| 第 1、2 天 | 100 |
| 第 3、12、18、21、24、27 天 | 300 |
| 第 7、10、15、20、25 天 | 500 |
| 第 4～6、8～9、11、13～14、16～17、19、22～23、26、28～29 天 | 200 |
| 第 30 天 | 1,000 |
| 第 31～99 天（除下列特殊日） | 500 |
| 第 66 天 | 666 |
| 第 88 天 | 888 |
| 第 100 天 | 1,000 |
| 第 101 天起 | 500 |

第 30 天按特殊奖励 1,000 积分优先处理。第 6、9 天遵循明确指定的 200 积分，不套用三的倍数规则。奖励配置和计算函数位于 `packages/domain/index.ts`，规则版本为 `streak-v1`。客户端不能指定奖励金额或连续天数；预览与发放均使用同一服务端规则。

初始 500 分只作用于新建账户，不重置已有钱包。历史签到记录和已发金额保留，同一天重复领取返回原记录；已连续签到的旧用户在下一天继续原连续天数，并按新规则计算当天金额。本地演示与云端共用该逻辑，真实云端生效需部署更新后的云函数及小程序。

广告会话和奖励记录原子更新，按北京时间自然日的成功领取次数发放 200、500、1,000 分，每日最多 3 次，共 1,700 分。观看中途退出不占次数；00:00 后从第一档开始。后端在实际领取事务中计算档位，避免并发会话重复占用同一档或绕过上限；观看前展示的金额为当时档位，多设备并发时最终金额以到账结果为准。领取结果丢失时使用原会话重试，不能重复领。旧会话已经发放的奖励保留原金额，不补发差额。

分享采用用户明确选择的**自行确认**方式，每次 100 分、不设每日次数上限。`share.start` 建立记录，`share.claim` 在用户确认后把钱包、流水和会话结果一次性提交。记录 `confirmation: self-reported`，不声称验证微信发送成功，也不区分收件人是好友还是群聊。好友页和钱包通过 `services/shares.ts` 共用待确认记录，一次处理一笔，领取或取消后可继续下一次；领取响应丢失会保留原标识，返回后重试，不重复加分。打开转发面板、回到页面、生成或复制邀请码均不会自动加分。

分享次数不限且依赖用户自报，无法防止虚假确认；这是当前明确选择的业务规则。云端需要新增仅管理端可访问的 `share_sessions` 集合（见 `cloudbase/database.json`）。本地模式只影响本机演示积分；真实转发面板与发送过程仍需微信环境验证。

## 6. 相对原方案的具体调整

- 按最新要求把所有工程文件放在 `_mock` 内，新增修改昵称与广告奖励，取代原方案“不做广告、使用固定昵称”的范围。
- 小规模好友关系以每用户最多 50 个 ID 的 `friend_lists` 文档存储，接受/移除时事务同时更新双方；不额外创建关系表与人数表。
- 第一版规则在版本化源码常量中维护，修改规则必须同步修改版本并重新构建部署；暂未实现管理后台或动态 `game_rules/app_config` 开关。历史结算不重新计算，原结果仍可查询。
- 邀请令牌使用云端随机数生成，仅管理端可读的集合保存；暂未额外哈希存储令牌。一次性、有效期、调用归属和生成频率均有校验。
- 工程采用一个根依赖与构建入口，前后端源文件按目录分层，暂不拆为多个 npm workspace 包；共享代码在构建时打入正确产物。
- 设置提供开奖震动开关；本版未加入音频素材。

## 8. 界面维护与离线布局检查

当前首页按用户确认的场景方向重做：整张绿色绒布桌面、木质桌边、透明骰盅、盅内立体骰子和桌面筹码，所有玩法直接铺在桌上；钱包、好友和个人页共用色彩、按钮与表单状态。昵称和邀请码的错误保留在字段旁，好友管理提供可见移除入口。结算已成功时，历史刷新失败只显示记录错误，不重新进入待恢复状态。

设计规范见 [DESIGN.md](DESIGN.md)，交互约定见 [UX-CONTRACT.md](UX-CONTRACT.md)，运行时 token 位于 `apps/miniprogram/styles/tokens.wxss`。修改基础样式后运行 `npm run check`。原始技术方案作为历史设计保留，其中的旧目录描述不再作为当前导入路径。

`node scripts/visual-review.mjs` 读取本地构建后的实际页面控制器、WXML 和 WXSS，生成 `dist/visual-review/` 下的静态状态页面。它仅用于布局复核，不是新增 Web 产品，也不支持点击试玩。若已有 Playwright，可设置 `VISUAL_PLAYWRIGHT` 为它的 `index.mjs` 绝对路径，按需设置 `VISUAL_BROWSER` 为本机 Chrome 路径，再执行此脚本生成 320/390px 截图和 `report.json`。继续执行 `node scripts/verify-table-motion.mjs` 可检查真实 CSS 摇盅、骰子弹跳、立体旋转、落定及减少动态偏好，结果保存为 `motion-report.json`。此辅助脚本不向项目添加浏览器依赖。

Premium 检查结果见 `docs/verification/`。静态审计不解析 WXML/WXSS，离线预览也不能替代微信开发者工具、软键盘、读屏、真机和云端广告验证。

### 摇盅场景说明

场景采用 WXML/WXSS 分层与 CSS 立体变换。透明盅壁和反光位于骰子前方，骰子轨迹限制在盅内；这属于 2.5D 表现，不是物理碰撞引擎。正常开奖先摇动约 1.8 秒，再用 320ms 落定；网络慢时等待确认，积分和最终正面点数始终来自业务服务。断线恢复直接查询原局，不重新生成结果。支持减少动态偏好，不新增 npm 依赖。
